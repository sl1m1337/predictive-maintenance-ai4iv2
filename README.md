Програмний комплекс машинного навчання та пояснюваного ШІ (Explainable AI) для раннього прогнозування відмов промислових верстатів за телеметричними даними датчиків.

> **Версія 2.0 (Enterprise Edition)** доповнює систему звітною документацією, аналітикою відмов, симулятором порогу рішень, розширеним набором тестів, контейнеризацією та CI. Базова логіка навчання (LightGBM + SMOTE), формули фізичних ознак, пороги `τ_п = 0.25` / `τ = 0.50` та перші три вкладки інтерфейсу залишилися без змін, тому всі наведені нижче метрики актуальні.

## Що нового у версії 2.0

- **Протокол технічної діагностики агрегату** (вкладка 1). Документ містить дату й час перевірки, показники датчиків з контролем допустимих діапазонів, розраховані ΔT і P, імовірність відмови, рівень критичності, топ-3 фактори впливу за SHAP, перевірку механізмів відмов AI4I 2020 та інженерні рекомендації. Завантажується у форматах TXT і JSON.
- **Зведений CSV-звіт пакетного аналізу** (вкладка 2). Для кожного запису подано рівень критичності, вердикт системи, головний фактор ризику за SHAP, виконані критерії механізмів відмов, вихід показників за допустимі діапазони та рекомендовану дію. Кодування UTF-8 з BOM, тож кирилиця коректно відкривається в Excel.
- **Вкладка «4. Аналітика відмов та симулятор порогів»**. Показує розподіл типів відмов TWF / HDF / PWF / OSF / RNF і частоту відмов за серіями L / M / H. Інтерактивний симулятор порогу τ ∈ [0.10; 0.80] миттєво перераховує Precision, Recall, F1-Score та кількість пропущених аварій на тестовій вибірці.
- **8 модульних тестів** замість 4. Нові тести не потребують мережі: модель навчається на синтетичному журналі у форматі AI4I 2020.
- **Dockerfile** для розгортання Streamlit-додатку та **GitHub Actions** для запуску `pytest` при кожному push.

## Архітектура системи

Проєкт побудований за модульною схемою (модулі М1–М7):

- **`config.py`** — централізована конфігурація гіперпараметрів, фізичних ознак та порогів ризику (`τ_п = 0.25`, `τ = 0.50`).
- **`src/data_loader.py` (М1)** — завантаження журналу телеметрії AI4I 2020, очищення та валідація схеми даних, стратифіковане розбиття 80/20 до балансування.
- **`src/feature_engineering.py` (М2)** — синтез похідних фізичних ознак: температурного перепаду (`Temp_diff_K`) та механічної потужності на шпинделі (`Power_W`).
- **`src/model_engine.py` (М3)** — балансування навчальної вибірки методом `SMOTE` (1:1), навчання ансамблевих моделей (`LightGBM`, `XGBoost`, `CatBoost`) та дворівнева класифікація ризиків.
- **`src/explainer.py` (М4)** — глобальна та локальна інтерпретація прогнозів на основі значень Шеплі (`SHAP TreeExplainer`) із контролем адитивності.
- **`app.py` (М5)** — інтерактивний веб-інтерфейс на базі `Streamlit` (онлайн-діагностика, пакетний аналіз CSV, порівняння метрик, аналітика відмов).
- **`src/report_generator.py` (М6, нове у v2.0)** — формування протоколу технічної діагностики (TXT / JSON) та зведеного CSV-звіту пакетного аналізу; контроль допустимих діапазонів датчиків; оцінка механізмів відмов за фізичними критеріями AI4I 2020; генерація інженерних рекомендацій.
- **`src/failure_analytics.py` (М7, нове у v2.0)** — розподіл типів відмов, частота відмов за серіями обладнання, метрики бінарного рішення для довільного порогу та їх візуалізація.
- **`train_benchmark.py`** — консольний модуль відтворення експериментальних результатів та графіків.
- **`tests/test_pipeline.py`** — набір модульних тестів (`pytest`).

### Модуль М6 — `src/report_generator.py`

| Функція | Призначення |
| :--- | :--- |
| `build_diagnostic_protocol(...)` | Структурований протокол діагностики одиничного агрегату (словник) |
| `render_protocol_text(protocol)` | Текстовий документ протоколу (UTF-8) для `st.download_button` |
| `protocol_to_json(protocol)` | Машиночитаний JSON (для інтеграції з CMMS / ERP) |
| `build_batch_report(...)` | Зведена таблиця результатів пакетного аналізу |
| `batch_report_to_csv(report)` | CSV-файл звіту (UTF-8 з BOM) для `st.download_button` |
| `check_sensor_limits(obs)` | Контроль виходу показників датчиків за допустимі діапазони |
| `evaluate_failure_mechanisms(obs)` | Перевірка критеріїв TWF / HDF / PWF / OSF / RNF |
| `generate_engineering_recommendations(...)` | Рекомендації за рівнем критичності, механізмами відмов і факторами SHAP |

Механізми відмов оцінюються за критеріями з опису набору AI4I 2020 (S. Matzka, 2020):

| Код | Механізм | Критерій |
| :--- | :--- | :--- |
| TWF | Знос інструменту | знос 200–240 хв |
| HDF | Порушення тепловідведення | ΔT < 8.6 K та оберти < 1380 об/хв |
| PWF | Відмова за потужністю | P < 3500 Вт або P > 9000 Вт |
| OSF | Перевантаження | знос × момент > 11 000 / 12 000 / 13 000 хв·Нм (L / M / H) |
| RNF | Випадкова відмова | 0,1 % незалежно від параметрів |

Статус «НАБЛИЖЕННЯ» позначає, що до межі критерію залишилось менше 10 %.

### Модуль М7 — `src/failure_analytics.py`

| Функція | Призначення |
| :--- | :--- |
| `compute_failure_type_distribution(raw_df)` | Кількість і частка кожного типу відмов |
| `summarize_failure_modes(raw_df)` | Загальна кількість відмов і перекриття типів |
| `failure_rate_by_equipment_type(raw_df)` | Частота відмов за серіями L / M / H |
| `compute_threshold_metrics(y, p, τ)` | TP, FP, FN, TN, Precision, Recall, F1 за правилом `p ≥ τ` |
| `threshold_sweep(y, p)` | Метрики на сітці порогів 0.10 … 0.80 (крок 0.01) |
| `plot_*` | Графіки розподілу відмов, кривих метрик і компромісу FN / FP |

## Веб-інтерфейс

| Вкладка | Зміст |
| :--- | :--- |
| 1. Інтерактивна діагностика агрегату | Повзунки датчиків, ΔT і P, імовірність відмови, рівень ризику, локальний SHAP. **v2.0:** завантаження протоколу діагностики (TXT / JSON) |
| 2. Пакетний аналіз телеметрії (CSV) | Аналіз вибірки AI4I 2020 або власного CSV. **v2.0:** завантаження зведеного CSV-звіту |
| 3. Метрики якості моделі | Порівняльна таблиця LightGBM / XGBoost / CatBoost |
| 4. Аналітика відмов та симулятор порогів | **v2.0:** розподіл типів відмов, симулятор порогу τ ∈ [0.10; 0.80] |

Нові елементи вкладок 1 і 2 розміщено **під** наявним вмістом, тому верхня частина цих вкладок виглядає так само, як у версії 1.0.

Симулятор порогу лише відтворює метрики для іншого значення τ і не змінює робочі пороги системи. За `τ = 0.50` він використовує ту саму тестову вибірку (2000 записів) і те саме правило рішення, що й вкладка 3, тож має відтворювати метрики LightGBM з таблиці нижче.

## Модульні тести

| № | Тест | Що перевіряє |
| :---: | :--- | :--- |
| 1 | `test_physical_features_calculation` | Обчислення ΔT та P = M · ω |
| 2 | `test_risk_classification_thresholds` | Дворівнева класифікація ризику (0.25 / 0.50) |
| 3 | `test_schema_validation_missing_column` | Виявлення відсутніх стовпців телеметрії |
| 4 | `test_stratified_split_preserves_ratio` | Стратифіковане розбиття 80/20 |
| 5 | `test_diagnostic_protocol_generation` | Структура й зміст протоколу, топ-3 SHAP, рекомендації, експорт TXT / JSON |
| 6 | `test_shap_additivity` | Адитивність SHAP (`check_additivity`) та узгодженість із `predict_proba` |
| 7 | `test_sensor_boundary_values` | Граничні значення датчиків, виявлення значень поза діапазоном, межі порогів |
| 8 | `test_batch_prediction_correctness` | Пакетний прогноз, метрики порогу проти `sklearn`, зведений CSV-звіт |

Тести 6–8 навчають основний конвеєр (SMOTE + LightGBM + SHAP) на синтетичному журналі у форматі AI4I 2020 і не завантажують дані з мережі.

## Швидкий старт

```bash
# 1. Встановлення залежностей
pip install -r requirements.txt

# 2. Запуск модульних тестів
pytest -v

# 3. Запуск експериментального бенчмарку
python train_benchmark.py

# 4. Запуск веб-інтерфейсу діагностики
streamlit run app.py
```

## Запуск через Docker

```bash
# Збірка образу
docker build -t predictive-maintenance-ai4i:2.0 .

# Запуск веб-інтерфейсу: http://localhost:8501
docker run --rm -p 8501:8501 predictive-maintenance-ai4i:2.0

# Запуск модульних тестів у контейнері
docker run --rm predictive-maintenance-ai4i:2.0 pytest -v
```

Примітки:
- Під час першого відкриття сторінки додаток завантажує набір AI4I 2020 з репозиторію UCI, тому контейнеру потрібен доступ до інтернету.
- Протоколи діагностики фіксують час у часовому поясі `Europe/Kyiv`. Інший пояс можна задати так: `docker run -e TZ=Europe/Warsaw ...`.
- Контейнер працює від непривілейованого користувача та має `HEALTHCHECK` (`/_stcore/health`).

## Безперервна інтеграція (GitHub Actions)

Workflow `.github/workflows/tests.yml` запускає `pytest -v` на Python 3.10 при кожному `push` і `pull request`. Його також можна запустити вручну з вкладки **Actions**. Залежності кешуються за `requirements.txt`.

Щоб бейдж статусу тестів на початку README працював, замініть `YOUR_GITHUB_USERNAME` на ваш логін GitHub (і назву репозиторію, якщо вона інша).
